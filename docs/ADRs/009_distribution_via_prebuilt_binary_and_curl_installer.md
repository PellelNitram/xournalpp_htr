# ADR 009 – Distribute via Prebuilt Binary and `curl | bash` Installer

- Date: 2026-11-23
- Status: Proposed (draft for review)
- PRD: None
- Drivers: Martin Lellep ([@PellelNitram](https://github.com/PellelNitram/))
- Deciders: Martin Lellep ([@PellelNitram](https://github.com/PellelNitram/))

## Context

Installing `xournalpp_htr` today means cloning the repo, running
`INSTALL_LINUX.sh` (git clone of `HTRPipeline`, a Dropbox model download,
`uv sync`, `xournalpp-htr-configure`) and hand-editing `plugin/config.lua`.
This is Linux-only and too heavy for non-developers. The milestone
[Installation](https://github.com/PellelNitram/xournalpp_htr/milestone/3) aims
to replace this with a download-and-run experience built by CI.

Existing facts this plan builds on:

- The Lua plugin (`plugin/main.lua`) already shells out via `os.execute` to
  `python_executable run_htr.py -if <xopp> -of <pdf>`. Swapping in a binary is
  a one-line change.
- The [PyInstaller PoC](../PoCs/simplify_installation_with_single_file_executable.md)
  already produced a working Linux binary (then with bundled `htr_pipeline`
  models).
- The native pipeline has reached parity, which lifts the condition of
  [ADR 008](008_keep_htr_pipeline_until_native_parity.md):
  `2026-11-23_online_word_detector_hub_simple_htr_ondb_beam_vocab` (stroke-based
  word detector + SimpleHTR-OnDB, beam search + word list) is the current best
  pipeline (see [OnlineHTR](../models/online_htr.md)). **The binary bundles this
  pipeline and `htr_pipeline` is dropped** (#125).

## Decision

1. **Ship a prebuilt binary per OS** (PyInstaller, one-dir mode), containing
   the CLI (`run_htr`) and the default pipeline with its models.
2. **Build it in GitHub Actions** with an OS matrix (Linux first, then
   Windows). Releases use CalVer `YYYY.MM.PATCH` (e.g. `2026.12.0`, hotfix
   `2026.12.1`), computed by CI. See [CI/CD flow](#cicd-flow).
3. **Install via one command**:
   `curl -fsSL https://github.com/PellelNitram/xournalpp_htr/releases/latest/download/install.sh | bash`
4. **The plugin calls the binary**, not Python. `config.lua` is generated by
   the installer.
5. **Two modes only**: *user* (binary, nothing else) and *developer*
   (clone + `uv sync`, as today). A separate "model developer" mode is just
   developer mode plus training extras (see ADR 006).
6. **Platform order**: Linux, then Windows (PowerShell `install.ps1`). macOS
   only once requested in a GitHub issue.

## Final setup

### Release contents (per OS)

```
xournalpp-htr-<os>-<arch>.zip
├── xournalpp_htr/           # PyInstaller one-dir bundle
│   ├── run_htr              # entry point (run_htr.exe on Windows)
│   └── _internal/...        # libs + models
├── plugin/
│   ├── main.lua
│   ├── plugin.ini
│   └── config.lua.template
└── SHA256SUMS               # published next to the zip, checked by install.sh
```

### What `install.sh` does

1. Detect OS and architecture; pick the matching zip.
2. Download zip and checksum from the release, verify SHA256.
3. Unpack to `~/.local/share/xournalpp-htr/<version>/`, symlink `current`.
4. Find the Xournal++ plugin directory (native `~/.config/xournalpp/plugins/`;
   Flatpak and snap paths detected; ask if none found).
5. Copy `plugin/` there and write `config.lua` pointing at the binary.
6. Print a success message and the shortcut (`Ctrl+F1`).

Each release ships its own `install.sh`, and CI writes that release's version
into it when publishing. A script therefore always installs the release it
was downloaded from, and the URL alone picks the version:

| URL | Installs |
|---|---|
| `.../releases/latest/download/install.sh` | Latest stable release |
| `.../releases/download/2026.12.0/install.sh` | Exactly `2026.12.0` |
| `.../releases/download/nightly/install.sh` | Current `nightly` |

There is no `--version` flag. Flags: `--uninstall`, `--plugin-dir <path>`.

### CI/CD flow

Every trigger runs the same build job per OS: `pyinstaller run_htr.spec`,
smoke test on a tiny `.xopp` fixture plus its pre-rendered PDF (no Xournal++
needed, see [Xournal++ dependency](#xournal-dependency)), zip. A release is only published if the
smoke test passes.

| Trigger | Result | Audience |
|---|---|---|
| Pull request | Build + smoke test, zip as workflow run artifact | Review |
| Push to `master` | Same, plus overwrite the rolling `nightly` pre-release | Testing on own machines |
| Monthly cron (1st of the month) | If commits since the last tag: compute next CalVer, tag, publish Release | Users |
| Manual button (`workflow_dispatch`) | Same as cron, on demand (hotfixes) | Users |

- **Workflow run artifacts** live on the run page (Actions tab), need a GitHub
  login, expire after 90 days and have no stable URL, so they are for
  development only.
- **Version computation**: find the latest `YYYY.MM.*` tag; same month →
  bump PATCH, new month → `YYYY.MM.0`. Cron and button share this logic.

### The `nightly` pre-release

*Pre-release* and *nightly* are not two kinds of release. *Pre-release* is a
checkbox GitHub offers on any release: the release is labelled as such and
`releases/latest` skips it. *`nightly`* is the name of the one release of ours
that has this checkbox set. Monthly and hotfix releases never set it.

**Purpose.** Monthly releases are the only builds users get. `nightly` closes
the gap between "merged to `master`" and "released":

- Test the latest `master` exactly as a user would (real `install.sh`, real
  zip, real plugin) on the Linux and Windows machines, before the monthly
  release picks it up.
- Hand a fix to someone who reported a bug without waiting up to a month or
  cutting a hotfix release.
- Workflow run artifacts cannot do this: they need a login, expire, have no
  stable URL and are not what `install.sh` downloads.

**How it works.** On every push to `master` whose build and smoke test pass,
CI:

1. Moves the git tag `nightly` to the new commit (force-update).
2. Replaces all assets of the GitHub Release `nightly` (zips, `SHA256SUMS`,
   `install.sh`) with the fresh ones, keeping it marked as *pre-release*.
3. Writes the commit SHA and build date into the release notes, so a bug
   report against `nightly` names the exact commit.

There is always exactly one `nightly`, never a history of them. Its URL is
stable, `.../releases/download/nightly/install.sh`; `releases/latest` ignores
pre-releases, so the user curl command never installs it. Install it with:

```bash
curl -fsSL https://github.com/PellelNitram/xournalpp_htr/releases/download/nightly/install.sh | bash
```

Re-running the monthly install command switches back to the stable release.

### Local execution

CI logic lives in `Makefile` targets and scripts, and the workflow YAML only
calls them (thin workflows). The same commands run locally on the Linux and
Windows machines:

| Target | Does |
|---|---|
| `make build-binary` | `pyinstaller run_htr.spec` + zip into `dist/` |
| `make smoke-test-binary` | Run the built binary on the `.xopp` fixture |
| `make install-local` | Run `install.sh` against the local `dist/` zip (no download) |
| `scripts/next_calver.sh` | Print the next CalVer tag (dry run of the release logic) |

Only the publishing steps (tagging, uploading release assets) need GitHub and
stay CI-only.

Debugging the workflow YAML itself locally is out of scope for this ADR.
[`act`](https://github.com/nektos/act) could replay the Linux workflows in
Docker if that need comes up later (it cannot emulate Windows runners).

### Development life cycle

```
merge to master ──► nightly updated ──► test on own Linux/Windows machines
                                          │
                       ┌──────────────────┴──────────────────┐
                    all good                        bug in released version
                       │                                     │
          1st of month: cron publishes      fix ──► merge ──► nightly ──► verify
          YYYY.MM.0 (if anything changed)                     │
                                             manual button publishes YYYY.MM.(N+1)
```

1. Every merge to `master` updates `nightly`.
2. `nightly` is installed and used on the Linux and Windows machines; this is
   where regressions are noticed before users see them.
3. On the 1st of the month the cron publishes `YYYY.MM.0` if anything was
   merged since the last release.
4. If a bug in the current release is serious enough not to wait: fix it,
   merge, verify the fix on `nightly`, then press the manual button. It runs
   the same workflow as the cron and publishes the next PATCH, e.g.
   `2026.12.1`.

Monthly and hotfix releases are the same workflow with a different trigger,
so there is only one release path to maintain.

## User experience

**Install**

```bash
curl -fsSL https://github.com/PellelNitram/xournalpp_htr/releases/latest/download/install.sh | bash
```

**Use**

1. Open Xournal++, write notes, save the document.
2. Menu *Plugin → Xournal++ HTR* (or `Ctrl+F1`).
3. Choose where to save; a searchable PDF is written there.

**Update** (re-running the install command installs the latest release over
the current one):

```bash
curl -fsSL https://github.com/PellelNitram/xournalpp_htr/releases/latest/download/install.sh | bash
```

**Uninstall** (removes `~/.local/share/xournalpp-htr/` and the plugin folder;
the HF Hub model cache is left alone and printed for manual removal):

```bash
curl -fsSL https://github.com/PellelNitram/xournalpp_htr/releases/latest/download/install.sh | bash -s -- --uninstall
```

Prerequisite: Xournal++ itself is installed, see below.

## Xournal++ dependency

Producing the searchable PDF needs a render of the `.xopp` as PDF. Today the
Python code calls `xournalpp <file> -p <out.pdf>` from `$PATH`
(`utils.export_to_pdf_with_xournalpp`). That breaks for the binary on Windows
(Xournal++ is rarely on `PATH`), for Flatpak/snap installs (the command is
`flatpak run com.github.xournalpp.xournalpp`) and in CI (no Xournal++, no
display).

**Proposal: the plugin renders the PDF, the binary only adds the text layer.**
The plugin runs inside Xournal++, which can export the open document itself
via the Lua API (`app.export`, Xournal++ ≥ 1.2). The plugin exports to a
temporary PDF and calls

```
run_htr -if notes.xopp --input-pdf /tmp/xyz.pdf -of notes_searchable.pdf
```

- No Xournal++ path to find or configure on any OS or packaging.
- The smoke test runs on a committed `.xopp` + PDF fixture pair, so CI needs
  no Xournal++.
- Needs a new `--input-pdf` option; without it the CLI keeps calling
  `xournalpp` as today (developer mode, scripts).
- To verify in a POC: `app.export` produces the same PDF as `xournalpp -p`.

**Fallback if `app.export` falls short: a configured path.** The binary takes
`--xournalpp <command>`; the installer detects Xournal++ and writes it into
the plugin config, which the user can edit:

```lua
-- ~/.config/xournalpp/plugins/xournalpp_htr/config.lua
_M.htr_executable = "/home/me/.local/share/xournalpp-htr/current/xournalpp_htr/run_htr"
_M.xournalpp_executable = "xournalpp"                                     -- native, on PATH
-- _M.xournalpp_executable = "flatpak run com.github.xournalpp.xournalpp"  -- Flatpak
-- _M.xournalpp_executable = "/home/me/Apps/Xournal++.AppImage"            -- AppImage
-- _M.xournalpp_executable = [[C:\Program Files\Xournal++\bin\xournalpp.exe]]  -- Windows
```

## Consequences

### Pros

- One command for users; no Python, uv, git or Dropbox download.
- Plugin and binary are versioned together and always in sync.
- Every push yields testable artifacts; releases are automatic (monthly,
  only if something changed) with a manual override.

### Cons

- Binary size (bundled models and libs) and per-OS build maintenance.
- `curl | bash` requires trust; mitigated by version pinning, checksums and a
  short readable script.

## Open questions

1. **Models**: bundle in the zip or download on first run? Pipelines already
   fetch their models from the HF Hub at runtime and cache them
   (`inference_models.py`), so downloading on first run keeps the zip small and
   lets users pick any other pipeline whose code and runtime are in the binary
   (ONNX/numpy). Pipelines needing `torch`/`transformers` (TrOCR) or a local
   export (OnlineHTR) are not available in the binary. Bundling only the
   default pipeline's models would add offline support.
2. **Dependencies**: does the default pipeline run without `torch` (ONNX /
   numpy only)? That decides binary size. Verify in the spike.
3. **Flatpak/snap Xournal++**: can the plugin execute a binary outside the
   sandbox?
4. **Xournal++ dependency**: does `app.export` replace the `xournalpp -p`
   call, or is the configured-path fallback needed? See
   [Xournal++ dependency](#xournal-dependency).

## Alternatives

- **`pip`/`pipx install`**: still requires Python and does not install the
  Lua plugin.
- **Single-file PyInstaller binary**: simpler to ship but unpacks on every
  launch; slow startup.
- **Native packages (deb, AppImage, MSI)**: better UX per platform but much
  more maintenance. Revisit if the curl installer proves insufficient.
- **Docker**: wrong fit for a desktop plugin calling a local binary.
