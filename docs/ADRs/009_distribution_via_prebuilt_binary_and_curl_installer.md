# ADR 009 – Distribute via Prebuilt Binary and `curl | bash` Installer

- Date: 2026-11-23
- Status: Proposed (draft for review)
- PRD: None
- Drivers: Martin Lellep ([@PellelNitram](https://github.com/PellelNitram/))
- Deciders: Martin Lellep ([@PellelNitram](https://github.com/PellelNitram/))

## Context

Installing `xournalpp_htr` today means cloning the repo, running
`INSTALL_LINUX.sh` (git clone of `HTRPipeline`, a Dropbox model download,
`uv sync`, `xournalpp-htr-configure`) and hand-editing `plugin/config.lua`.
This is Linux-only and too heavy for non-developers. The milestone
[Installation](https://github.com/PellelNitram/xournalpp_htr/milestone/3) aims
to replace this with a download-and-run experience built by CI.

Existing facts this plan builds on:

- The Lua plugin (`plugin/main.lua`) already shells out via `os.execute` to
  `python_executable run_htr.py -if <xopp> -of <pdf>`. Swapping in a binary is
  a one-line change.
- The [PyInstaller PoC](../PoCs/simplify_installation_with_single_file_executable.md)
  already produced a working Linux binary (then with bundled `htr_pipeline`
  models).
- The native pipeline has reached parity, which lifts the condition of
  [ADR 008](008_keep_htr_pipeline_until_native_parity.md):
  `2026-11-23_online_word_detector_hub_simple_htr_ondb_beam_vocab` (stroke-based
  word detector + SimpleHTR-OnDB, beam search + word list) is the current best
  pipeline (see [OnlineHTR](../models/online_htr.md)). **The binary bundles this
  pipeline and `htr_pipeline` is dropped** (#125).

## Decision

1. **Ship a prebuilt binary per OS** (PyInstaller, one-dir mode), containing
   the CLI (`run_htr`) and the default pipeline with its models.
2. **Build it in GitHub Actions** with an OS matrix (Linux first, then
   Windows). Releases use CalVer `YYYY.MM.PATCH` (e.g. `2026.12.0`, hotfix
   `2026.12.1`), computed by CI. See [CI/CD flow](#cicd-flow).
3. **Install via one command**:
   `curl -fsSL https://github.com/PellelNitram/xournalpp_htr/releases/latest/download/install.sh | bash`
4. **The plugin calls the binary**, not Python. `config.lua` is generated by
   the installer.
5. **Two modes only**: *user* (binary, nothing else) and *developer*
   (clone + `uv sync`, as today). A separate "model developer" mode is just
   developer mode plus training extras (see ADR 006).
6. **Platform order**: Linux, then Windows (PowerShell `install.ps1`). macOS
   only once requested in a GitHub issue.

## Final setup

### Release contents (per OS)

```
xournalpp-htr-<os>-<arch>.zip
├── xournalpp_htr/           # PyInstaller one-dir bundle
│   ├── run_htr              # entry point (run_htr.exe on Windows)
│   └── _internal/...        # libs + models
├── plugin/
│   ├── main.lua
│   ├── plugin.ini
│   └── config.lua.template
└── SHA256SUMS               # published next to the zip, checked by install.sh
```

### What `install.sh` does

1. Detect OS and architecture; pick the matching zip.
2. Download zip and checksum from the release, verify SHA256.
3. Unpack to `~/.local/share/xournalpp-htr/<version>/`, symlink `current`.
4. Find the Xournal++ plugin directory (native `~/.config/xournalpp/plugins/`;
   Flatpak and snap paths detected; ask if none found).
5. Copy `plugin/` there and write `config.lua` pointing at the binary.
6. Print a success message and the shortcut (`Ctrl+F1`).

Flags: `--version vX.Y.Z`, `--uninstall`, `--plugin-dir <path>`.

### CI/CD flow

Every trigger runs the same build job per OS: `pyinstaller run_htr.spec`,
smoke test on a tiny `.xopp` fixture, zip. A release is only published if the
smoke test passes.

| Trigger | Result | Audience |
|---|---|---|
| Pull request | Build + smoke test, zip as workflow run artifact | Review |
| Push to `master` | Same, plus overwrite the rolling `nightly` pre-release | Testing on own machines |
| Monthly cron (1st of the month) | If commits since the last tag: compute next CalVer, tag, publish Release | Users |
| Manual button (`workflow_dispatch`) | Same as cron, on demand (hotfixes) | Users |

- **Workflow run artifacts** live on the run page (Actions tab), need a GitHub
  login, expire after 90 days and have no stable URL, so they are for
  development only.
- **`nightly`** is a pre-release with a fixed tag and a stable URL
  (`.../releases/download/nightly/...`). `releases/latest` ignores
  pre-releases, so the user curl URL never points at it. Test with
  `curl ... /releases/download/nightly/install.sh | bash -s -- --version nightly`.
- **Version computation**: find the latest `YYYY.MM.*` tag; same month →
  bump PATCH, new month → `YYYY.MM.0`. Cron and button share this logic.

## User experience

**Install**

```bash
curl -fsSL https://github.com/PellelNitram/xournalpp_htr/releases/latest/download/install.sh | bash
```

**Use**

1. Open Xournal++, write notes, save the document.
2. Menu *Plugin → Xournal++ HTR* (or `Ctrl+F1`).
3. Choose where to save; a searchable PDF is written there.

**Update**: re-run the install command. **Uninstall**: `install.sh --uninstall`.

Prerequisite: Xournal++ itself is installed (the binary renders `.xopp` via
`xournalpp` on `$PATH` or a configured path).

## Consequences

### Pros

- One command for users; no Python, uv, git or Dropbox download.
- Plugin and binary are versioned together and always in sync.
- Every push yields testable artifacts; releases are automatic (monthly,
  only if something changed) with a manual override.

### Cons

- Binary size (bundled models and libs) and per-OS build maintenance.
- `curl | bash` requires trust; mitigated by version pinning, checksums and a
  short readable script.

## Open questions

1. **Models**: bundle in the zip or download on first run? Pipelines already
   fetch their models from the HF Hub at runtime and cache them
   (`inference_models.py`), so downloading on first run keeps the zip small and
   lets users pick any other pipeline whose code and runtime are in the binary
   (ONNX/numpy). Pipelines needing `torch`/`transformers` (TrOCR) or a local
   export (OnlineHTR) are not available in the binary. Bundling only the
   default pipeline's models would add offline support.
2. **Dependencies**: does the default pipeline run without `torch` (ONNX /
   numpy only)? That decides binary size. Verify in the spike.
3. **Flatpak/snap Xournal++**: can the plugin execute a binary outside the
   sandbox?
4. **Does `xournalpp` need to be found by the binary** (PATH vs configured
   path), and what do we do when it is missing?

## Alternatives

- **`pip`/`pipx install`**: still requires Python and does not install the
  Lua plugin.
- **Single-file PyInstaller binary**: simpler to ship but unpacks on every
  launch; slow startup.
- **Native packages (deb, AppImage, MSI)**: better UX per platform but much
  more maintenance. Revisit if the curl installer proves insufficient.
- **Docker**: wrong fit for a desktop plugin calling a local binary.
